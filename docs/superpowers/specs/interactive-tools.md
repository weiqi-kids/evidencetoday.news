# Spec：工具型頁面（互動查詢工具）

> **狀態：規格，未動工。業主已標記為「大工程」。** 本檔的產出是可供決策的界線與階段拆解。
> **定位：** 有一群讀者不是來讀文章的，他們是來**查一個數字**（能帶幾瓶、要停幾天、放幾天會壞、我符不符合資格）。
> 這些人現在得讀完整篇文章才拿得到那個數字。工具頁把那段路縮短，並在給完數字之後把人送回文章。

---

## 0. 這份規格要業主決定的三件事

1. **第一個做哪個**（本檔的推薦見 §8，理由已寫；要換就換）
2. **工具頁走 `src/pages/`，不新增 content collection** —— 接受嗎？（影響守門，見 §6）
3. **§3 的醫療界線畫在哪** —— 本檔畫得偏保守（輸入端就不收身體資料）。這條放寬會省事，但也會把工具從「查規則」變成「做判斷」。

## 1. 候選是掃過站上實際內容才列的

**教訓：曾經憑數據挑 10 個題目，其中 6 個站上早就有了。** 所以本節的候選一律先掃內容再列，
而且列的是**內容叢集**（同一題目已經有一批文章互相支撐），不是單篇。

自己重掃的方式（本檔不寫篇數，數字會腐爛）：

```bash
# 各類型有多少、排到哪天
pnpm stats
# 曝光／點擊／排名／Top 著陸頁（判斷哪些叢集真的有人在查）
pnpm perf
# 按主題掃站上有沒有寫過（換關鍵字重跑）
grep -h "^title:" src/content/*/*.md* | grep -E "帶回|入境|保存|常溫|放多久|篩檢|公費|換算|一起吃"
```

判斷一個叢集適不適合做成工具，用三個條件（要全中）：

1. **讀者要的是一個離散答案**（數字、能／不能、符合／不符合），不是一段理解。
2. **答案由一張可窮舉的規則表決定**，且每一格都追得到官方文件。
3. **站上已經有一批文章在寫這個叢集**——工具是把既有內容的骨架抽出來，不是新開題目。
   缺這條的工具會變成一個沒有內容支撐的空殼頁，過不了 §5 的 SEO 要求。

## 2. 候選清單

### A. 境外保健品／藥品「帶得回台灣嗎」查詢 ⭐

- **站上叢集**：`import-melatonin-taiwan-customs`、`thailand-sleep-gummies-bring-back-taiwan`、
  `japan-drugstore-medicine-bring-back-taiwan`、`cbd-products-bring-back-taiwan-legal-risk`、
  `nmn-taiwan-legal-buy`、韓國藥局／紅蔘、GLP-1 針劑、日本藥妝保健食品等。
  題型規範已經有專檔：[`../../page-rules/international-regulation.md`](../../page-rules/international-regulation.md)。
- **輸入**（全部封閉選項）：入境方式（隨身攜帶／郵寄網購）、成分或品項（下拉，只列站上有專文的項目）、有無醫師處方。
- **輸出**：該品項在台灣的法規定位（藥品／食品／管制藥品／查無明文）、限量規則的**原文摘引**、
  規則出處連結與公告日期、以及「這題完整說明在哪一篇」。
- **規則來源**：關務署「入境旅客攜帶自用藥物限量表」、食藥署郵寄輸入規定、藥事法條號——
  這些已經逐條寫在上述文章的 `references` 裡，工具只是把它們結構化。
- **紅線風險**：低。輸出的是法規條文，不是醫療判斷。但要守 §3 的措辭規範，不做個案法律結論。

### B. 食物在冰箱／常溫能放多久

- **站上叢集**：冰箱保存總表、蛋（常溫買回要不要冰、浮水法、放門邊）、常溫豆漿、包餡麵包、
  滷味攤、自助餐保溫檯、切開的水果、自製蒜頭油、米與黃麴毒素。
- **輸入**：食物類別、保存方式（常溫／冷藏／冷凍）、是否已開封／已煮熟。
- **輸出**：時間區間 ＋ 「什麼情況直接丟」的判準 ＋ 出處（食藥署／FDA FoodKeeper）。
- **紅線風險**：最低。非醫療內容，不涉及個人身體狀況。

### C. 公費篩檢／疫苗資格查詢

- **站上叢集**：公費癌症篩檢資格總整理、肺炎鏈球菌疫苗劑次改制、帶狀疱疹疫苗各縣市補助、幽門螺旋桿菌公費篩檢。
- **輸入**：年齡區間、生理性別、少數封閉的資格條件（例如有無家族史選項——這一項要斟酌，見 §3）。
- **輸出**：符合哪些公費項目、頻率、依據的公告與其日期。**不輸出「你該不該打／該不該篩」**。
- **紅線風險**：中。資格判定本身是行政事實，但「要不要做」是醫療決定，措辭必須嚴格分開。

### D. 抗凝血／抗血小板藥 × 保健品或食物 查詢

- **站上叢集**：黑木耳、魚油、納豆激酶、阿斯匹靈＋魚油、磷蝦油、紅麴＋statin、生物素、甲狀腺素＋鈣鐵、抗生素＋益生菌。
  `pnpm perf` 的機會查詢裡，這個叢集的問句形狀（「吃某某藥可以吃某某嗎」）長期有量。
- **輸入**：藥物類別（下拉，不收藥名自由文字）、保健品或食物（下拉）。
- **輸出**：這個組合**有沒有被官方或指引記載為需要注意**、記載的證據等級、以及該篇文章連結。
- **紅線風險**：**最高**。這是最容易滑進「可以吃／不能吃」的題型。放最後做，且規則表必須經醫療審閱掛名
  （流程見 [`../../playbooks/medical-review.md`](../../playbooks/medical-review.md)）。

### E. 抽血／手術前保健品停用天數

- **站上叢集**：`biotin-before-blood-test`（抽血前生物素）、肌酸與肌酸酐誤判。
  **但「術前停用幾天」這個題目站上還沒有**（掃過 `術前｜停用｜手術前` 沒有命中）。
- **結論**：不合格 —— 違反 §1 條件 3。**要做這個工具，得先補文章**。列在這裡是為了記下「已經查過、目前不成立」。

### F. 劑量單位換算（IU ↔ µg／mg）

- **站上依據**：脂溶性維生素會不會超標、劑量決定毒性。
- **性質**：純機械換算，零判斷成分，紅線風險為零。
- **結論**：單獨成頁太薄，過不了 §5 的內容量要求。**當成 A 或 C 的內嵌小元件**，不獨立立頁。

## 3. 硬規則 7 的界線：工具能輸出什麼、不能輸出什麼

這一節是本檔最重要的部分。工具跟文章的差別在於它會**針對使用者的輸入**吐出一個答案，
那個形狀天生就靠近「醫療建議」。界線要畫在能機械檢查的地方，不能靠寫的人當下的判斷力。

### 可以輸出

- 法規事實：限量、分類、罰則條號、公告日期
- 官方文件裡的數值，以及該數值的出處連結
- 機械換算（單位、時間、體積、重量）
- 行政資格：符合／不符合某項公費方案的條件
- 「這個組合有沒有被記載為需要注意」＋ 該記載的證據等級
- 「下一步該問誰」：科別或主管機關（不指名特定醫師或院所）

### 不可以輸出

- 個人化劑量：「你應該吃 X mg」「你可以吃到 Y」
- 個案安全判定：「你這樣可以吃」「這樣不安全」
- 行動指令：停藥、停用、加量、改用、延後手術
- 依使用者輸入的**症狀或檢驗數值**做的分級、風險分數、診斷傾向
- 任何「本工具建議……」的措辭

### 措辭規範（可以逐條 review）

**主詞永遠是規則或來源，不是使用者。**

| ❌ 不要寫 | ✅ 改成 |
|---|---|
| 你可以帶 2 個月的量 | 衛福部會同財政部公告的自用藥物限量，無醫師處方者以 2 個月用量為限 |
| 這個組合不安全 | 這個組合被列在某某指引的注意事項，證據等級為某某 |
| 建議術前停用 7 天 | 某某指引記載的停用時間為某某天；實際是否停用由開刀的醫師決定 |
| 你符合資格，建議去篩檢 | 依某某公告，這個條件符合公費篩檢資格 |

### 輸入端的防線（最乾淨的一條界線）

**工具不收症狀、不收檢驗數值、不收用藥清單自由文字。輸入一律是封閉選項（下拉、單選）。**

理由有兩層：

1. 一旦工具開始吃使用者的身體資料，它輸出的東西在形式上就變成針對個人的健康判斷，
   §3 上半段的界線會變得很難守。
2. 蒐集健康資料在個資法上是另一個層級的事（特種個資）。靜態站沒有後端，資料理論上不離開瀏覽器，
   但只要輸入框存在，就會有人把它當成問診窗口。**不開這個口，就不用管理這個風險。**

⚠️ 候選 C 的「有無家族史」屬於健康資料的邊緣。第一版**不放這個選項**，只用年齡與生理性別；
需要家族史才判定的項目，直接輸出「這一項的資格條件包含家族史，請看某某公告／某某篇文章」。

## 4. 技術路徑

### 頁面與資料的擺放

| 東西 | 放哪 | 為什麼 |
|---|---|---|
| 工具頁 | `src/pages/tools/<slug>.astro` | 走 `src/pages/`，**不新增 content collection**。理由見 §6 |
| 規則資料 | `src/data/tools/<slug>.json` | 它是結構化規則，不是給人讀的文章。與 `src/data/policies/` 的擺法同源 |
| 互動層 | `src/components/tools/<Name>.svelte`，`client:visible` | 與 `EvidenceScale` 同 hydration 策略 |

### 三條技術決策

**1. 無 JS 也要能用，而且答案的全集要在 SSR 的 HTML 裡。**

這是本節最重要的一條。Astro 是零 JS baseline（見 [`../../architecture.md`](../../architecture.md)），
工具頁應該做成：**完整規則表先靜態渲染出來，Svelte 島嶼只負責過濾與高亮**。

反面做法是「一個表單 ＋ JS 算出答案」——那樣的頁在爬蟲與 LLM 眼裡是一張空白頁，
`check:site` 也會判它內容過薄。用漸進增強的做法，SEO、AEO、無障礙三件事一次解決，不用各做一遍。

**2. 不要 d3。**

這些工具是查表與篩選，不是資料視覺化。`d3-charts.md` 記的那一整批坑（高度傳遞鏈、
`<astro-island>` 預設 `display: inline`、simulation 收斂）只在「要撐滿容器的圖表」才會遇到，
查詢工具不需要付這個成本。

唯一可能需要 d3 的是「劑量落在建議區間的哪裡」這種數線視覺化。真的要做時，
照 [`../../playbooks/d3-charts.md`](../../playbooks/d3-charts.md) 的鎖定模式走，
特別是 `astro-island { display: block; height: 100% }` 那一條。

**3. URL 只有一個，不用 query string 產生變體。**

`/tools/<slug>/?item=melatonin` 會讓 Google 看到無限多個近乎重複的 URL。
篩選狀態放元件內部（或 hash），**不進 canonical**。

至於「每個品項一個靜態子頁」的做法：第一版不做。理由是那些子頁會跟既有文章搶同一批查詢，
正好撞上 `international-regulation.md` 的紅線 1（不要在同主題疊第二篇同角度的文）。

### 靜態站的限制（寫進規格，避免日後有人以為可以繞過）

- **沒有伺服器，不能查即時法規 API。** 規則資料在 build 時進 bundle，時效由人維護（見 §7）。
- 資料變更要 push 才會生效，走既有部署流程（push `main` → 自動 build → 部署）。
- 每筆規則資料必須帶 `verifiedAt`（查證日）與 `sourceUrl`／`sourceDate`，頁面要把查證日顯示出來。
  這一條沿用 `international-regulation.md` 的「有效期限與變動風險」規範，不另立一套。

## 5. SEO / AEO

工具頁要同時對搜尋引擎與 LLM 有意義，靠的是**它本來就是一張有出處的規則表**，不是靠額外的 SEO 加工。

- **內容全集靜態渲染**（§4 決策 1）。這一條同時滿足 Google 與 LLM——兩者都讀不到 JS 算出來的答案。
- **`.txt` 端點**：沿用既有慣例（`src/pages/<type>/[slug].txt.ts`），
  給工具頁一份純文字版，開頭是規則摘要、結尾是來源清單。
- **llms.txt / llms-full.txt** 要把工具頁加進去（`src/pages/llms.txt.ts`）。
- **JSON-LD**：`WebPage`（主題涉及醫療時用 `MedicalWebPage`）＋ `FAQPage`（把最常見的幾組輸入寫成 Q&A）
  ＋ `BreadcrumbList`，來源用既有的 `buildCitations()` 輸出 `citation`。
  ⚠️ **不要用 `SoftwareApplication` / `Product` / `AggregateRating`**——
  `seo-and-feeds.md` 明文禁止加入不存在的 Product、Rating 或商業 schema，
  而且那類標記會讓工具頁在 SERP 上長得像一個產品。
- **GEO**：工具頁是 LLM 最容易整段引用的形狀（一張明確的規則表 ＋ 每格的官方出處）。
  站外權威的做法不需要為工具頁另開一套，沿用 [`../../playbooks/geo-offsite.md`](../../playbooks/geo-offsite.md)。
- **不要跟既有文章搶同一組查詢**。工具頁的 `title` 與 `description` 要寫成
  「查詢／對照」形狀，把「為什麼」讓給文章。判斷有沒有互相蠶食，上線後跑 `pnpm perf` 看同一組查詢的著陸頁有沒有換人。

## 6. 守門相容性（最容易卡住的地方）

先講結論：**工具頁走 `src/pages/tools/`，不新增 content collection。**
下表逐 gate 說明會發生什麼事。

| Gate | 掃什麼 | 工具頁會怎樣 | 要做什麼 |
|---|---|---|---|
| **`check:spec`**（七月標準） | `collectionOf()` 只認 `src/content/{articles,myths,ingredients,news}/` | **掃不到，不會被擋** | 不用做。⚠️ 反過來說，如果做成新 collection，`SPEC` 裡沒有那個 key，一樣掃不到——**等於那個 collection 完全沒有規格守門**。這是不新增 collection 的主因之一 |
| **`check:boilerplate`** | `COLLECTIONS` 六個 content collection | **掃不到** | ⚠️ 但**文章端會被掃到**：如果每篇文章都加同一段「用我們的查詢工具」，那段話會在 ≥3 篇出現，被 12 字 n-gram 抓成樣板。**規範：文章連到工具只放連結，不附固定說明段；真要寫一句，每篇各寫各的** |
| **`check:content`**（去 AI 味） | `src/**/*.md(x)` | **掃不到 `.astro`／`.svelte`** | 文案仍要手動守硬規則 8 的鐵則。工具頁的說明文字不進 gate，只能靠 review |
| **`check:design`** | `src/` 全部 `.css/.astro/.svelte` | **會掃到，這是最可能擋 build 的一道** | 見下方展開 |
| **`check:site`** 規則 1–4 | `DETAIL` 只有四個內容目錄 | 站內出口中位數、渲染重複率**不統計工具頁** | ⚠️ 硬規則 14 的精神仍然適用：工具頁自帶 ≥2 個站內出口（連回它的來源文章）。**工具頁數量到 3 頁以上時，建議把 `tools` 加進 `check-site.mjs` 的 `DETAIL`**，讓它受同一條規則管 |
| **`check:site`** 規則 5–6 | 掃 `dist/` 全部 html | **會掃到** | 工具頁要 indexable（在 sitemap 裡就不能是 noindex）；頁上所有站內連結不得死連 |
| **`pnpm build`** | 全部 | 硬規則 16：零錯誤才算通過 | — |

### `check:design` 展開（工具頁最會踩的四條）

工具頁有表單控制項，而表單是全站最容易寫出小字的地方：

1. **字級下限 18px，算出來的值也算。** input、select、option、label、單位說明、
   「資料查證日」這種角落文字**全部**都要 ≥18px，且一律走 `var(--text-*)`。
   規則 1a 是「算出來的值 < 18px 即擋」，寫 `0.85rem` 不會逃掉。
   （副作用剛好是對的：iOS Safari 在表單字級 <16px 時會自動縮放頁面，18px 下限順帶解決。）
2. **顏色只准 `var(--color-*)`。** 表單的 focus、error、disabled 狀態很容易順手寫 hex，會直接擋 build。
   要新色請走 [`../../playbooks/design-tokens.md`](../../playbooks/design-tokens.md)，不要在元件裡寫死。
3. **禁外部 CDN。** 不能用任何 CDN 載入的 UI 套件、圖示庫、下拉元件。
4. **樣式寫 scoped `<style>`**，不新增 `.css` 檔（`src/` 下只准 `variables.css` 與 `global.css`）。
   斷點只用 640/768/1024/1280，間距用 `clamp()`。

### 免責與揭露（硬規則 10）

工具頁**不寫醫療免責句**。頁尾已有一處，這頁跟其他頁一樣有頁尾。
工具頁需要的是**資料時效說明**（「本表依據某某公告，查證日 YYYY-MM-DD」），那不是免責，
放在表格下方、降彩度、字級不低於 `var(--text-meta)`。細則見
[`../../playbooks/legal-notices.md`](../../playbooks/legal-notices.md)。

## 7. 資料維護與審閱

- **法規資料的半衰期大約一年**（`international-regulation.md` 的判斷）。
  每個工具的規則檔要有一個複查到期日，寫進 [`../../reminders.md`](../../reminders.md)，
  到期時 session 啟動會主動提醒。
- **規則表視同內容，要走醫療審閱**：涉及藥品、交互作用、疫苗的工具，其規則表要掛 `reviewer`
  並記進 `docs/medical-review-queue.md`。純法規（帶回台灣）與非醫療（食物保存）的可先不掛，
  但要在頁上寫清楚資料來源與查證日。流程見 [`../../playbooks/medical-review.md`](../../playbooks/medical-review.md)。
- **同一份規則出現在兩個地方就會分岔**。工具的規則資料與文章正文講的規則必須一致；
  文章更新時要同步檢查工具資料，反之亦然。這是「一件事只寫在一個地方」在資料層的版本：
  **文章引用工具的數字時，用連結指過去，不要在正文再抄一次**。

## 8. 分階段：第一個做「境外保健品帶回台灣查詢」

| 階段 | 工具 | 為什麼是這個順序 |
|---|---|---|
| **Phase 1** | **A. 帶回台灣查詢** | 見下方四點 |
| **Phase 2** | B. 食物保存時間 | 驗證「工具頁模式」能不能複製到非法規題；紅線風險最低，可以放手做版面實驗 |
| **Phase 3** | C. 公費篩檢／疫苗資格 | 資料每年變動、需要維護節奏成熟後再做 |
| **Phase 4** | D. 交互作用查詢 | 紅線風險最高，且需要規則表逐條掛醫療審閱。前三個做完、界線經過實戰檢驗才動 |

**Phase 1 選 A 的四個理由**：

1. **它是唯一一個「站上已有整叢文章、且該叢確實是站上主要入口」的題目。**
   （現在還是不是，跑 `pnpm perf` 看 Top 著陸頁，本檔不寫數字。）
   讀者已經在那批頁面上找那個數字，工具是把既有需求接住，不是賭一個新需求。
2. **規則是法規條文，可以逐條追到官方公告，完全避開硬規則 7。**
   工具不必做任何醫療判斷，§3 的界線在這一題上幾乎不用費力守。
3. **資料量小，第一版可以純靜態 JSON ＋ 一個 Svelte 島嶼做完。**
   第一個工具的價值是驗證整套模式（守門、SEO、版面、維護節奏）跑不跑得通，
   拿一個資料量大的題目去驗證只會把驗證變慢。
4. **它天然是「讀者來查一個數字」的頁。** 這正是工具頁存在的理由，不需要說服讀者改變行為。

### Phase 1 的完成判準

- `pnpm build` 零錯誤，`check:design` / `check:site` 全綠
- 工具頁在無 JS 環境下規則表完整可讀
- 工具頁自帶 ≥2 個站內出口，且來源文章都連得到工具頁
- 上線一個完整觀測窗後跑 `pnpm perf`：確認工具頁有自己的曝光，**且來源文章的曝光沒有掉**
  （掉了代表在蠶食，要調 title/description 或收掉工具頁）
